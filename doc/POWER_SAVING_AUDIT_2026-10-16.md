# 절전 변경 검증 — 2026-10-16

대상: XIAO ESP32-C6, Thread/Matter, CC1101, PCF8575 LP_I2C, OLED, 700mAh 셀.  
요구: 하루 20~50회 조작, OLED 10초, 기존 명령 지연 유지, 15일 이상 사용.  
범위: 10월 13일 분석 이후 소스·설정·빌드 설정·저장된 NVS 실험 기록을 오프라인으로 재검증했다. 펌웨어 수정, 빌드, 플래시, 시리얼 접속, 실기 설정 변경은 하지 않았다.

## 1. 결론

**최근 변경에는 유효한 진단·복구 보강이 있다. 그러나 최근 며칠의 변경으로 정상 사용 배터리 수명이 늘었다는 증거는 아직 부족하다. 15일 사용도 입증되지 않았다.**

- TOP 전원 차단 설정과 SPI/RMT 리텐션은 추가되었다. 하지만 정상 운용 덤프에서는 TOP·MODEM이 계속 유지되어, 설정 추가를 실제 도메인 차단으로 볼 수 없다.
- LP 재적재 전 정지, 실험 중 LP 유지·단계별 폴링 확인, 핀 고정 해제 후 CC1101 VERSION 확인은 의미 있는 개선이다. 실험 때문에 망가진 상태를 정상 운용 개선과 혼동하지 않아야 한다.
- 기존 버튼의 100ms 통지 대기 뒤 10ms 추가 지연, main 100ms 주기, OLED OFF 500ms 주기는 여전히 남아 있다.
- 새 실제 실험은 MODEM·TOP·LP의 큰 소비 기여를 지지하지 않았다. 다만 이를 모두 “무죄”라고 단정하는 해석은 과도하다. **95% 상한의 시간축 계산에 오류가 있고, 실험과 정상 사용의 조건도 다르다.**
- 새 WAKE 교정은 파일 기준으로 `dry=1`인 모의 실행뿐이다. 실제 기상당 전하와 사용 시간 증가를 측정한 결과가 아니다.

따라서 현재 판정은 **“측정과 복구 도구는 발전했으나, 제품 절전 성과는 미검증”**이다. 효과가 전혀 없다고 단정하는 것도 현재 자료의 범위를 넘는다.

## 4. 새 MODEM·TOP·LP 실험의 인정 범위

세 실험 모두 COM7의 무선 시작 전 수동 light-sleep 비교다. 각 단계는 75분, 4단계, 5분 간격 61표본이다. 보조 COM8 파일에는 해당 `lsfloor` 표본이 없다.

| 실험 | 실제 바뀐 조건 | 차단·정지의 증거 | 데이터에서 인정할 수 있는 결론 |
|---|---|---|---|
| MODEM, 10/14~15 | MODEM ON/OFF | `0x3C02 ↔ 0x3C06` | 이 실험 조건에서 큰 반복 전압 차이를 검출하지 못함 |
| TOP, 10/15~16 | **TOP과 MODEM이 함께** ON/OFF | `0x3C12 ↔ 0x3C17` | CPU OFF 조건의 두 도메인 동시 변경에서 차이가 작음 |
| LP, 10/16 | LP 폴링 활동 ON/OFF | 약 **188.7→0→188.3→0회/초**; 플래그 `0x3C12` 유지 | 이 실험 조건에서 폴링 활동의 큰 전압 효과를 검출하지 못함 |

“차이를 검출하지 못함”과 “전류를 전혀 쓰지 않음”은 다르다.

### 조건 차이 1: MODEM 실험은 CPU가 꺼지지 않았다

MODEM 실험의 `0x3C02/06`에는 CPU 차단 비트 `0x10`이 없다. TOP·LP 실험에는 있다. MODEM 실험 자체의 ON/OFF 비교는 읽을 수 있지만, 그 결과를 CPU OFF인 정상 사용 또는 TOP 실험으로 그대로 옮길 수 없다. 서로 다른 조건의 전압 기울기를 빼서 부품별 전류를 배분해서도 안 된다.

### 조건 차이 2: TOP 실험은 단일 요인 분리가 아니다

`0x3C12 XOR 0x3C17 = 0x05`이므로 TOP(bit0)과 MODEM(bit2)이 함께 바뀐다. 앞선 MODEM 실험을 근거로 MODEM 기여를 0으로 놓고 남은 차이를 TOP에 귀속하는 것은 조건 차이와 상호작용 때문에 보장되지 않는다.

### 조건 차이 3: LP 폴링 정지는 LP 전체 전원 차단이 아니다

LP OFF 단계에서 폴링이 0인 것은 확인됐다. 다만 RTC/LP 주변장치의 유지 전력, PCF 정적 부하와 풀업 부하까지 모두 제거한 실험은 아니다. “LP 폴링 활동의 큰 효과가 안 보인다”까지는 말할 수 있지만 LP 관련 정적 소비 전체를 제외할 수 없다.

### 조건 차이 4: 무선 시작 전 비교로 정상 Thread 원인을 확정할 수 없다

진단과 정상 앱 사이에는 무선 스택, 기상 빈도, ADC·NVS 작업, CPU/DFS 및 GPIO 상태가 달라진다. “무선 없는 바닥이 작으므로 나머지 전부는 무선 스택” 또는 “바닥이 크므로 기상 최적화는 무의미”라는 결론은 모두 아직 성립하지 않는다.

## 5. 확인된 분석 오류와 과도한 판정

### 5.1 [P1] 95% 상한 계산에 실제보다 긴 표본 간격을 사용

[해석기 254~258행 부근](/D:/dev/workspaces/somfy-blinds-things-by-claude/sim/tools/lsfloor_decode.py:254)은 앞 1/3을 버린 표본 수에 대해 **전체 75분**을 나누어 시간 간격을 계산한다.

```text
실제: 남은 표본도 약 5분 간격
코드: 전체 75분 / (남은 11표본 - 1) ≈ 7.5분 간격
```

시간 분산 Sxx를 실제보다 크게 놓으므로 기울기 표준오차가 실제 시각을 쓴 값의 약 2/3로 작아진다. 기존 계산에서 표준오차 산정의 시간축만 실제 표본 시각으로 바꾸어 재현한 결과는 다음과 같다.

| 실험 | 기존 기울기 SE | 실제 시각 사용 SE | 기존 전류 상한 출력값 | 시간축만 수정한 계산값 |
|---|---:|---:|---:|---:|
| MODEM | 0.449mV/h | **0.674mV/h** | 0.563mA | **1.062mA** |
| TOP | 0.282mV/h | **0.422mV/h** | 0.862mA | **1.174mA** |
| LP | 0.501mV/h | **0.752mV/h** | 0.000mA | **0.047mA** |

재계산도 기존의 독립 오차·환산계수 가정을 유지한 비교용 값이며, 유효한 95% 보장으로 새로 인증한 값은 아니다. 셀 완화, 시간 상관, 단계별 체계 오차, 작은 반복 수, 전압→전류 환산계수 불확실성은 여전히 남는다.

특히 LP의 “0.0mA 미만” 출력은 `max(0, 계산값)`으로 자른 결과다. 전류가 0임을 측정한 것이 아니며, 음의 추정값과 모델 불일치를 0이라는 확정 상한으로 바꾸면 안 된다. 큰 차이가 확인되지 않았다는 점과 모든 원인이 제외됐다는 주장은 분리해야 한다.

재현: [독립 재계산 스크립트](/D:/dev/workspaces/somfy-blinds-things-by-claude/doc/assets/power_saving_2026-10-16/recompute_statistics.py). 기존 해석기와 펌웨어는 변경하지 않았다.

### 5.2 [P1] “실작업 703µs”를 모든 기상에 적용해 최적화 이득을 단정

[배터리 로그 해석기](/D:/dev/workspaces/somfy-blinds-things-by-claude/sim/tools/batlog_decode.py:120)는 과거 `somfy_app` 루프 한 번의 작업량 703µs를 모든 수면 복귀에 동일하게 빼서 “오버헤드 작음 — 루프 주기를 늘려도 이득이 작다”라고 출력한다.

main, 버튼, OLED, 무선 기상은 작업량이 다르며, 이 계산에는 수면 함수 내부의 전원 전환 에너지도 충분히 분리되지 않는다. 이 자동 판정은 측정에 따른 전류 절감 상한이 아니다. 이 문구를 근거로 이벤트 대기 전환을 기각하면 안 된다.

### 5.3 [P2] 태스크 반복 통계의 분모가 PM 비교 창과 다름

[COM7 LP 후 텍스트 기록](/D:/dev/workspaces/somfy-blinds-things-by-claude/logs/batlog_COM7_1016_lpnight.txt)에는 main 52,925회 / 세션 12,120초 = 4.37회/초가 나온다. 그러나 같은 덤프의 PM 정상 운용 비교 창은 5,223.984초다. 이 창 길이로 단순 참고 계산하면 약 10.13회/초로 소스의 100ms 주기와 부합한다.

정확한 반복 빈도는 시작·종료 양쪽의 태스크 계수를 같은 창에서 빼야 한다. 위 10.13도 동일 창의 완전한 차분으로 확정한 값은 아니다. 다만 **4.37회/초라는 출력만 보고 main이 10→4회/초로 개선됐다고 판단할 수 없음**은 분명하다. `전체 기상 - 태스크 반복 합`을 무선 스택 몫으로 귀속하는 계산도 중복 대기·창 불일치 때문에 신뢰할 수 없다.

`poll_ms=25`, 예상 버튼 40회/초도 현재 100ms 설정과 맞지 않는 옛 통계 값이다. 출력 라벨이 실제 실행 경로를 대표하는지 먼저 확인해야 한다.

### 5.4 [P2] 현재 WAKE 교정은 모의 실행이며 검사도 보강 필요

최신 [WAKE 덤프](/D:/dev/workspaces/somfy-blinds-things-by-claude/logs/nvs_COM7_1016_1711_wakedry.bin)는 `fac=3`, `dry=1`, 20초×5단계, 21표본이다. B 단계는 sleep 성공 횟수가 아니라 모의 루프 횟수를 포함한다. 해석기 자체도 `DRY`를 출력한다.

향후 실제 실험을 하더라도 다음을 보강해야 한다.

- 펌웨어 B 루프는 수면 실패 때도 `n++`하고, 한 표본에는 마지막 플래그만 남긴다. `analyse_wake()`는 현재 CPU 차단, 표본의 `rej`·USB·기상 원인·run 상태를 엄격히 거부하지 않는다. 실패 시도가 정상 기상으로 세어질 가능성을 막아야 한다.
- 무선 시작 전 수동 sleep + 고정 700µs busy 작업은 실제 자동 PM·RTOS·서로 다른 태스크의 기상과 같지 않다. 정상 앱의 직접 전류 차이로 최종 검증해야 한다.
- CC1101 IDLE **1.7mA는 전형 사양**이며 현 보드 배터리 측정으로 교정한 정밀 기준 부하가 아니다. `±20%`도 코드의 가정이다. 비율 기반 참고 환산과 추적 가능한 전류 교정을 구분한다. [TI CC1101 데이터시트](https://www.ti.com/lit/ds/symlink/cc1101.pdf)

## 6. 아직 남아 있는 실제 수정 후보

### 버튼 중복 대기는 그대로다

[LP 버튼 분기](/D:/dev/workspaces/somfy-blinds-things-by-claude/main/button_handler.c:1025)의 통지 대기 뒤, [공통 10ms 지연](/D:/dev/workspaces/somfy-blinds-things-by-claude/main/button_handler.c:1068)이 실행된다. 중복 대기를 제거하면 조용한 유휴의 명목 대기 복귀 지점은 약 18.18→10회/초로 줄어든다. 실제 전체 기상 감소와 mA 효과는 아직 측정되지 않았다.

이전 리포트의 “추가 약 12시간” 등은 **기상당 50µC 가정의 계획 계산**이다. 이번 WAKE 모의 실험은 그 50µC를 검증한 것이 아니다. 최근 변경의 실측 성과로 재사용하면 안 된다.

### main·OLED·hold의 이벤트 대기 전환도 미적용이다

현재 main 끝은 100ms, OLED OFF는 500ms, hold 기본은 500ms다. 먼저 입력·진동·Matter·송신 상태 변경이 태스크를 즉시 깨우도록 연결한 뒤 유휴 주기를 줄이는 것이 적절하다. 버튼 해제·짧은 탭·빠른 로터리·송신 중 조합 변경과 5초 WDT를 함께 검증해야 한다.

Thread slow poll 7초 / fast poll 200ms와 OLED 10초는 기존 요구대로 유지한다. 이 변경 없이도 가능한 HP 기상 정리가 남아 있다. 자동 light-sleep은 다음 작업과 타이머 시각의 영향을 받으므로, 실제 줄어든 기상을 같은 PM 창에서 확인해야 한다. [Espressif 전원 관리 문서](https://docs.espressif.com/projects/esp-idf/en/v5.5.5/esp32c6/api-reference/system/power_management.html)

## 7. 현재 배터리 사용 시간을 얼마나 믿을 수 있는가

새 덤프를 기존 전류 해석기로 재현하면 COM7은 세션 전체 약 **16.74mA**, 링 구간 약 **4.76mA**, COM8은 **“구간 없음”**이 나온다. 이들을 현재 제품의 확정 전류로 채택하지 않는다.

이유는 다음과 같다.

1. NVS 링에 과거와 현재 세션이 섞여 경과시간이 되돌아간다. COM8의 첫 행 31,450초가 마지막 행 30,247초보다 크다.
2. 시작 100% 클리핑과 출발 전압·충전 완화가 있다. COM8은 4176→4106mV인데 모델상 마지막도 약 100%에 가깝다. 짧은 구간에서 이 모델로 전류를 정확히 구분하기 어렵다.
3. COM7은 실험 후 정상 앱으로 돌아온 계수와 이어받은 세션 정보가 섞인다. 같은 창과 같은 세션으로 다시 잘라야 한다.
4. COM7/COM8은 설정, 셀·전압, 경과시간이 다르다. 두 평균을 바로 빼서 개선 mA를 산정하지 않는다.

**현재의 보수적 결론:** 과거 CC 보정 후 기록의 약 4.56mA는 역사적 모델 기준으로 남지만, 최근 변경 후의 새 확정 전류나 수명은 아직 산출할 수 없다. 700mAh 전량이면 약 6.4일, 여유 20%이면 약 5.1일이라는 과거 환산도 현재 빌드의 15일 보장이 아니다.

15일 목표는 여전히 전체 평균 **1.56mA 이하**(560mAh 가용 가정)다. 하루 50회·10초의 추가 부하와 통신 여유를 포함하면 이전 시나리오의 대기 약 1.1mA 목표가 필요하다. 새 자료에서 이 수준을 달성했다는 근거는 없다.

## 8. 다음 검증 순서

1. **해석기부터 바로잡는다.** 실제 tail 표본의 시각으로 회귀 오차를 계산하고, 여러 세션을 분리하고, PM·태스크 계수의 창을 일치시킨다. 모형 상한과 실측 전류를 구분한다.
2. **진단 기능과 제품 기능을 별도로 평가한다.** LP stop/restart·핀 복귀는 복구 성공 여부로, 절전 변경은 정상 Thread에서의 전류 차이로 판정한다.
3. **같은 보드·같은 셀에서 버튼 중복 대기 한 항목만 비교한다.** CPU/ADC/Thread 설정을 고정하고 입력 성공률·기상·전류를 함께 남긴다.
4. **그다음 main/OLED/hold 이벤트 대기를 검증한다.** 여러 변경을 한꺼번에 넣지 않고, 각 단계가 기존 반응성을 유지하는지 확인한다.
5. **WAKE 실제 측정은 유효성 검사부터 보강한다.** 직접 전류 측정이 가능하면 배터리 경로의 안전한 측정 지점에서 전하를 확인하고, 어렵다면 알려진 실제 부하를 사용해 전압법의 한계를 명시한다.
6. **최종 평가는 정상 사용 20~50회/일과 15일 방전으로 한다.** 무선 시작 전 진단의 5시간 기울기나 dry 성공을 제품 수명으로 환산하지 않는다.
