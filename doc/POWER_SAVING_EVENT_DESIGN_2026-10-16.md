# 응답성을 유지하는 절전 구조 분석

- 분석일: 2026-10-16
- 대상: XIAO ESP32-C6, LP I2C PCF8575, 진동 입력, OLED, CC1101, Matter/Thread
- 조건: 700mAh, 하루 20~50회 사용, OLED 10초, SmartThings 지연은 현재 수준 유지
- 이번 작업: 소스 읽기와 설계 분석. 펌웨어 수정·빌드·플래시·실기 설정 변경 없음.
- 근거: 현재 작업본의 실행 코드. 코드 주석의 과거 2ms/25ms/고정 10ms 설명과 현재 실행 경로를 구분했다.

## 1. 결론

100ms를 늘리면 반응이 느려지는 것은 현재 구조에서 설명된다. 하지만 버튼과 진동에 즉시 반응하려면 HP 주 CPU가 항상 100ms마다 일어나야 하는 것은 아니다. LP 감지 속도는 유지하고, 입력 전달과 디바운스 확인을 필요한 순간에 실행하도록 정리하는 것이 우선이다.

다만 현재 LP 알림은 모든 상황에서 버튼 태스크를 깨우는 일반적인 통지가 아니다. HP가 light sleep에서 ULP 원인으로 복귀할 때만 연결된다. 따라서 알림 누락 경로를 해결하기 전에 안전망 대기를 길게 늘리면 다시 느려질 수 있다. 현재 코드 그대로 무한 대기에 넣는 변경은 적절하지 않다.

## 2. 느려지는 구체적인 경로

### 2.1 LP 감지 주기와 HP 확인 주기는 다르다

- LP_POLL_US는 5000us이다. 실제 반복 주기는 I2C 실행 시간 등이 더해진다.
- LP는 매 회 PCF8575를 읽고 로터리 이동을 누적하며 버튼 눌림을 래치한다.
- HP 버튼 태스크는 유휴 상태에서 최대 100ms 통지 대기를 한다.
- LP의 빠른 감지와 HP의 느린 소비가 공존한다. HP 주기만 늘려도 LP 검출 속도가 느려지는 것은 아니지만, 입력이 사용자 동작으로 처리되는 시간은 느려질 수 있다.

근거: main/lp_core/pcf_lp_config.h의 LP_POLL_US, main/lp_core/pcf_poll.c:129~184, main/button_handler.c:1025.

### 2.2 첫 변화 뒤에도 100ms를 기다릴 수 있다

현재 버튼 디바운스는 raw_state가 변하면 시각을 저장하고, 이후 다시 확인하여 기본 20ms 이상 유지되었을 때 눌림을 확정한다.

반면 빠른 대기를 선택하는 any_held는 확정 상태 last_state만 본다. 처음 눌린 것을 관측했어도 아직 디바운스 중이면 any_held가 false여서 다시 100ms 대기로 들어갈 수 있다. 계속 누른 채 다른 변화나 통지가 없다면 20ms 확인이 100ms 대기 뒤로 밀린다.

따라서 주석의 ‘LP 검출 뒤 약 3~5ms 반응’은 버튼 이벤트 확정과 실제 RF 출력 전체의 보장이 아니다. 처음 관측하는 시간과 사용자 명령이 발생하는 시간은 따로 재야 한다.

근거: main/button_handler.c:778~792, 1016~1026.

### 2.3 통지 대기 뒤에 추가 10ms 지연이 있다

LP 경로에서 ulTaskNotifyTake가 끝난 뒤 BOARD_PCF_INT_ISR가 꺼져 있으면 공통 vTaskDelay(10ms)도 실행된다. 통지가 와도 다음 입력 처리를 즉시 시작하는 구조가 아니다.

정리 방향은 루프당 대기 지점을 하나로 만드는 것이다. 10ms를 단순 삭제하고 끝내기보다 디바운스·롱프레스·진동 재활성 시한을 통합하여 다음에 필요한 시각에만 기다리도록 설계해야 한다.

근거: main/button_handler.c:1025~1068.

### 2.4 진동은 인터럽트가 있어도 처리 전달은 폴링이다

현재 진동 ISR은 인터럽트를 마스킹하고 카운터를 증가시키며 끝난다. 버튼 태스크에 통지하지 않는다.

그 뒤 버튼 루프의 _vibration_track이 ISR 카운터 차분을 보고 진동 시각을 갱신한다. 메인 루프가 다시 그 시각을 확인하여 화면을 켠다. 즉 ‘하드웨어가 CPU를 깨움’과 ‘앱이 진동을 처리함’ 사이에 주기적 확인 두 단계가 남아 있다.

진동 인터럽트 재활성은 3회 루프, 고장 판정은 200표본, HIGH 검출 창은 30표본에 의존한다. HP 대기 시간을 바꾸면 이들의 실제 시간 폭도 함께 바뀐다. 예를 들어 입력 없는 반복이 약 110ms라면 200표본은 약 22초로, 과거 주석의 2초와 달라진다. 실제로는 통지 횟수에 따라 달라진다.

근거: main/button_handler.c:928~970, 1413~1437, 1510~1572; main/somfy_app.c:5869~5889, 6312.

## 3. 권장 구조

~~~mermaid
flowchart TD
    P[PCF8575 버튼·로터리] --> L[LP: 현재 5ms 설정으로 감지·기록]
    L --> M[공유 이벤트 보존 / 소비 확인]
    M --> I[입력 처리 태스크]
    V[진동 GPIO] --> G[최소 ISR: 이벤트 기록·폭주 차단·통지]
    G --> I
    I --> D[디바운스 중에만 짧게 재확인]
    D --> E[확정된 입력 이벤트]
    E --> R[RF 명령 큐 / 기존 송신 작업]
    E --> U[UI 갱신 통지]
    G --> Q[진동 유효성·고장 판정]
    Q --> U
    U --> O[화면 켜기 / 10초 종료 시한 갱신]
    O --> W[화면 OFF: 변경 통지를 기다림]
    T[기존 Matter/Thread 수신] --> R
    T --> U
~~~

이 도식은 구현 방안이다. 현재 LP→HP 전달의 빈틈을 이미 해결했다는 의미는 아니다.

| 작업 | 입력이 없는 동안 | 입력이 있을 때 | 정리할 핵심 |
|---|---|---|---|
| LP 입력 감지 | 우선 현재 5ms 설정 유지 | 버튼·로터리 기록 | 로터리 손실을 피하며 HP 최적화와 분리 |
| HP 입력 처리 | 통지 + 검증된 안전망 대기 | 미확정 입력도 활성 상태로 취급 | last_state뿐 아니라 디바운스 진행 여부 고려 |
| 디바운스 | 주기 실행 불필요 | 첫 변화 후 확인 시한에 재실행 | 기본 20ms 정책과 정상 입력 판정 유지 |
| 길게 누름·조합키 | 눌림이 없으면 대기 | 눌림·뗌·조합 변경·RF 완료로 깨움 | 송신 작업과 독립성 유지, 프레임 경계 중단 보존 |
| 진동 | 정상 상태에서 GPIO 감지 | 한 번 통지 후 짧은 관찰/시간 기반 재활성 | 잡음 폭주·HIGH 고정 고장 차단을 함께 설계 |
| 메인 제어 | 다음 실제 처리 시한까지 대기 | 입력·Matter·전원 상태 변화에 응답 | 상시 100ms 확인을 기능별 시한으로 분리 |
| OLED | OFF이면 통지 대기 | 통지 즉시 켜고, 필요한 동안 현재 갱신 | 500ms 대기를 길게 늘리는 방식 대신 즉시 통지 |
| Thread | 현재 설정 유지 | 현재 명령 전달 유지 | slow 7000ms / fast 200ms를 절전 첫 수단으로 바꾸지 않음 |

OLED는 현재 첫 버튼 콜백에서 _exit_sleep을 통해 직접 켜지고 화면도 렌더한다. 따라서 모든 버튼 표시가 메인 루프 100ms를 기다린다고 보면 틀린다. 다만 고우선순위 버튼 처리에서 화면 렌더까지 수행하므로, 권장 구조에서는 입력 확정·RF 큐 등록과 UI 요청을 짧게 끝내고 실제 렌더는 UI 태스크가 맡도록 한다. 기존 UI 태스크 분리와 I2C 보호는 유지한다.

근거: main/somfy_app.c:1279~1322, 3927~3948; main/oled_ui.c:2854~2918, main/oled_ui.h:212~215.

## 4. 빠뜨리면 다시 느려지거나 불안정해지는 부분

1. **HP가 이미 깨어 있는 경우:** 현재 LP wake 요청만으로 버튼 태스크가 항상 통지되지는 않는다. 공유 메모리의 pending/seq와 소비 확인, 잠들기 직전 상태 변경을 포함한 전달 규약이 필요하다. 실제 IDF 실행 문맥에 맞는 방법을 확인하고 검증해야 한다. 단순히 통지 대기를 무한대로 바꾸지 않는다.
2. **짧은 탭 보존:** 현재 래치는 HP에서 한 번 읽으면 소비된다. ‘잠깐 눌린 것으로 보임’과 ‘HP 디바운스가 그 탭을 확정함’은 다르다. 눌림·뗌·순서를 판정 완료까지 보존하는 규칙이 필요하다. PROG의 잘못된 입력을 만들지 않는 것도 필수다.
3. **시간 기준 통일:** LP 정지 판정도 현재 8회 확인 기준이다. 진동의 3/30/200표본과 함께 실제 경과 시간으로 다시 정의해야 한다. LP 정지 시 눌림 상태가 고착되어 반복 송신되는 기존 실패를 막아야 한다.
4. **진동 알림 폭주:** ISR에 통지만 추가하면 잡음이 있을 때 더 많이 깨울 수 있다. 정상 이벤트의 즉시 통지, 마스킹, 시간 기준 재활성, 고장 상태에서 GPIO wake 차단과 복구를 함께 다룬다. 센서가 불안정하면 하드웨어 신호 상태도 확인해야 한다.
5. **5초 watchdog:** 메인·버튼 태스크를 길게 대기시키려면 현재 watchdog 구독과 생존 확인 정책을 같이 검토한다. 전역 watchdog을 끄는 방식으로 해결하지 않는다.
6. **PCF ~INT:** 현재 보드에서 유효성이 확인되지 않아 사용하지 않는 경로다. 이를 즉시 사용 가능한 해결책으로 전제하지 않는다. LP 감지를 우선 활용한다.

## 5. 권장 적용 순서와 검증

| 순서 | 분석상 변경 후보 | 통과해야 할 기준 |
|---|---|---|
| 1 | 디바운스 중 짧은 재확인, LP 경로 이중 대기 정리 | 첫 입력·짧은 탭·길게 누름·로터리·조합키 동작 유지 |
| 2 | 진동 처리와 UI 갱신을 직접 통지로 연결 | 첫 두드림 인식, 정지 중 오검출 없음, 고장 시 wake 폭주 없음 |
| 3 | 메인·OLED OFF·hold 유휴 폴링을 이벤트/시한 대기로 변경 | 화면 10초, RF 조합 전환, 전원 연결·분리, 설정·복구 동작 유지 |
| 4 | HP 기상 중 LP 입력 전달 및 생존 감시 검증 후 안전망 대기 조정 | HP 수면/기상 양쪽에서 누락 없음, LP 정지 시 반복 송신 차단 |
| 5 | 남은 상시 전류와 전원 도메인 원인 확인 | 배터리 단자에서 동일 조건 평균 전류 재측정 |

각 단계는 따로 측정한다. 여러 폴링 주기를 한꺼번에 늘리면 어떤 입력 경로가 느려졌는지 분리하기 어렵다. 100ms 안전망은 전달 검증 전까지 유지한다.

기록할 시각은 ‘물리 입력 → LP 관측 → HP 처리 → 디바운스 확정 → RF 요청 → 실제 송신 시작 → 화면 첫 갱신’이다. 첫 입력, OLED ON/OFF, HP가 이미 깨어 있는 경우, Thread 트래픽 중, NVS 쓰기 중을 구분한다. 평균뿐 아니라 느린 경우와 누락 건수를 본다. 이번에는 실기 측정을 실행하지 않았다.

## 6. 15일 목표와 기대 효과의 정량적 한계

700mAh 중 80%인 560mAh를 사용 가능하다고 가정하면 15일의 전체 평균 전류 예산은 1.556mA, 하루 사용량은 37.33mAh다. 80%는 설계 여유 가정이며 배터리 실측 용량이 아니다.

| 전체 평균 전류 | 하루 사용량 | 560mAh 기준 예상 사용 시간 |
|---:|---:|---:|
| 1.0mA | 24.0mAh | 23.3일 |
| 1.3mA | 31.2mAh | 17.9일 |
| 1.5mA | 36.0mAh | 15.6일 |
| 1.556mA | 약 37.3mAh | 약 15일 |
| 2.0mA | 48.0mAh | 11.7일 |
| 3.0mA | 72.0mAh | 7.8일 |

이는 실제 사용과 송신까지 포함한 전체 평균이다. 유휴 전류만 이 수치에 맞추면 충분한 것이 아니다.

예시로 화면이 켜질 때 유휴보다 전체 장치 전류가 50mA 더 든다고 가정하면, 하루 20~50회 × 10초는 하루 2.78~6.94mAh, 평균 0.116~0.289mA를 추가한다. 이때 유휴와 그 밖의 활동이 함께 쓸 수 있는 예산은 평균 약 1.44~1.27mA다. 50mA는 계산 예시이며 OLED 단독 전류나 실제 장치 측정값이 아니다. RF 사용량이 이 가정에 포함되지 않으면 별도로 차감해야 한다.

| 조치 | 확실히 기대하는 변화 | 지금 확정할 수 없는 것 |
|---|---|---|
| HP 입력 이중 대기 정리 | 불필요한 대기·재개 감소, 입력 처리 지연 완화 | 절감 mA와 추가 사용 일수 |
| 메인/OLED/hold 유휴 폴링 정리 | 입력 없는 동안 예약 기상 감소 | 태스크 기상 수 감소와 CPU 기상 수 감소의 일대일 대응 |
| 진동 직접 통지 + 폭주 차단 | 빠른 처리와 유휴 폴링 축소를 함께 설계 가능 | 잡음 있는 실제 센서에서의 절감량 |
| LP 5ms 유지 | 현재 입력 감지 특성 보존 | LP/I2C 상시 소비의 해소 |
| 실제 전원 차단 상태와 주변 회로 확인 | 폴링 이외 상시 소비 원인 분리 | 현재 자료만으로 15일 달성 보장 |

태스크 여러 개가 같은 CPU 기상에 함께 처리될 수 있으므로 폴링 횟수를 단순 합산하여 절감 전류를 계산하면 안 된다. 기상 횟수뿐 아니라 유휴 바닥 전류와 이벤트당 소비 전하를 함께 측정해야 한다.

추천 판단: OLED 10초와 LP 5ms를 먼저 희생하기보다, 입력 전달·디바운스·진동·유휴 작업 예약을 정리한다. 그 뒤에도 평균이 1.556mA를 넘으면 LP/I2C, 켜진 전원 도메인, 보드 및 주변 장치의 상시 소비를 줄이는 단계가 필요하다. 이번 코드 분석만으로 event-driven 전환이 15일을 보장한다고 결론 낼 수는 없다.
