# OLED I2C · 배터리 표시 진단 시뮬레이터

> 배터리 % 표시 로직은 `bat_pct_display_sim.py` — 아래 「부록」 참조.

실기 없이(또는 실기 투입 전에) OLED I2C 문제를 좁히기 위한 파이썬 시뮬레이터 4종.
2026-07 "화면이 멈춘다" 문제를 추적하며 만들었고, 실제로 **원인을 좁히고 펌웨어
로직을 사전 검증**하는 데 사용했다.

> 프로젝트 규칙: **빌드/플래시 전에 로직을 파이썬으로 먼저 검증**한다.
> 아래 스크립트는 그 규칙을 OLED I2C 영역에 적용한 것이다.

| 스크립트 | 답하는 질문 |
|---|---|
| `adc_oled_mutex_sim.py` | **직렬화(뮤텍스) 설계가 전송 손상을 막는가** ★최신 |
| `oled_i2c_fault_sim.py` | 실측값과 일치하는 **고장모드는 무엇인가** |
| `i2c_bitbang_proto_sim.py` | 비트뱅 프로브 **로직이 맞는가**(플래시 전 검증) |
| `i2c_rise_time_sim.py` | 상승시간으로 **풀업 개수를 구분할 수 있는가** |

전부 `python <파일>` 로 실행하며 인자가 없다. 의존성 없음(표준 라이브러리만).

## 0. `adc_oled_mutex_sim.py` — 직렬화 설계 검증 (2026-08-11)

충전률 측정을 되살려도 OLED 가 안 깨지는지를 **플래시 전에** 판정한다.
FreeRTOS 를 흉내낸 초소형 **선점형 스케줄러**로 실제 태스크 우선순위를 재현한다.

```bash
python sim/tools/adc_oled_mutex_sim.py
```

모델의 핵심은 "동시 실행"이 아니라 **선점**이다. ESP32-C6 는 싱글코어라
`somfy_app`(prio 4)이 `oled_ui`(prio 3)를 밀어내고, 비트뱅은 CPU 가 곧 클럭이므로
밀려난 전송은 파형이 중간에 멈춰 SSD1306 을 고착시킨다.

**손상 판정**: 전송 1건이 진행 중일 때 *다른 태스크가 실제로 CPU 를 쓴 시간*을 누적해
20 µs 를 넘으면 손상. 락에 막혀 즉시 블록되는 것은 CPU 를 안 쓰므로 손상이 아니다
— 이 구분이 두 설계를 가르는 지점이다.

**래치 모델**: 손상 1건이 나면 `present=false` 가 되고, 그 뒤 flush 는 바깥 락을 잡기
**전에** return 해 재검출 probe 만 돈다. 이것이 "몇 분 뒤 멈춰서 안 돌아옴"의 정체다.

결과 (8시드 × 10분):

| 구성 | 손상 | 고착 | 고착된 회차 | 최빠른 고착 |
|---|---|---|---|---|
| A. 수정 전 (flush 만 락) | 7 | 7 | **6/8** | **80초** |
| B. 수정 후 (`_bbo_write` 가 락) | **0** | **0** | **0/8** | 없음 |
| C. 보호 없음(참고 상한) | 972 | 968 | 8/8 | 0초 |

배터리 측정은 두 구성 모두 952/952 성공 → **측정 주기(5초)·표본 수(8회)를 줄이지
않아도 기아가 없다**. 줄이면 오히려 `_nobat_track` 의 노이즈 상쇄 가정이 깨진다.

### 이 시뮬레이터를 만들며 잡은 함정 (재사용 시 주의)

- **주기가 정수배면 결과가 거짓이 된다.** 5 s / 50 ms / 10 ms 는 전부 정수배라
  지터 0 이면 기상 위상이 항상 같은 자리에 떨어져 충돌이 **구조적으로 회피**된다
  (첫 실행에서 "손상 0" 이 나온 원인 — 모델 인공물이었다). `JITTER_US` 로 위상을 흔든다.
- **시드 1개로 결론내지 말 것.** 위상 관계가 시드마다 달라 손상 건수가 크게 흔들린다.
  8시드를 합산한다.
- **`for op in gen: yield op` 는 `send()` 를 전달하지 않는다.** 반드시 `yield from`.
  이걸 틀려 락 획득 결과가 `None` 이 되고 unlock 이 실행되지 않아, "배터리 측정
  100 % 실패" 라는 가짜 결과가 나왔었다.
- **동시 기상 시 우선순위 순으로 처리**해야 한다. 낮은 쪽이 먼저 락을 채가면
  거짓 기아가 관측된다.

## 1. `oled_i2c_fault_sim.py` — 고장모드 ↔ 실측 대조

KiCad 넷리스트에서 뽑은 회로(풀업 위치·스위치·모듈)를 **저항 네트워크로 모델링**해,
각 고장 가설이 만들어낼 측정값(핀 float / 내부PD / 내부PU 레벨, bit-bang 스캔 결과)을
계산하고 **실기 측정값과 대조**한다. 일치하지 않는 가설을 기계적으로 탈락시킨다.

모델링한 고장모드: 정상 / 스위치 A위치 단락 / 모듈 미연결 / VCC↔GND 역전원 /
SDA↔SCL 교차 / 칩 사망 / SDA GND 단락.

```bash
python sim/tools/oled_i2c_fault_sim.py
```

**핵심 회로 사실**(이 스크립트에 인코딩돼 있음):

- **h4(신 PCB)** : I2C 풀업 4.7K(R8/R9)가 **PCB 에 있다** → 모듈이 없거나 무전원이어도
  버스는 HIGH 로 보인다. "버스가 정상이니 모듈이 연결됐다"고 추론하면 **틀린다**.
- **v4(구 PCB)** : I2C 에 **PCB 풀업이 없다** → 측정된 HIGH 는 곧 **모듈 자체 풀업**이므로
  모듈에 전원이 들어와 있다는 증거가 된다.

이 비대칭이 진단의 핵심이었다. 실측 대조 결과 COM7 은 "모듈 미연결 / SDA↔SCL 교차 /
칩 무응답" 3개로, COM4 는 "SDA 라인 GND 단락" 1개로 좁혀졌다.

## 2. `i2c_bitbang_proto_sim.py` — 비트뱅 프로토콜 검증

`test/somfy_cases/oled_only_test.c` 의 bit-bang 프로브와 **동일한 파형 시퀀스**를
파이썬으로 재현하고, SSD1306 슬레이브 상태머신을 모델링해 ACK 를 검증한다.
플래시하기 전에 로직 오류를 잡는 용도.

```bash
python sim/tools/i2c_bitbang_proto_sim.py
```

검증 항목 3가지:

1. 정상 배선에서 정방향 프로브가 `0x3C` 를 검출하는가
2. 교차 배선에서 정방향 프로브가 무응답인가 (실측과 같은 증상인가)
3. 교차 배선을 **핀을 맞바꾼 프로브**가 검출하는가

★부수 발견: 슬레이브가 ACK 후 SDA 를 놓지 않으면 **이후 전 주소가 거짓 ACK** 된다.
COM4 실측(`전 주소 응답`)과 정확히 같은 패턴이었고, 이 시뮬레이터로 재현해 확인했다.

## 3. `i2c_rise_time_sim.py` — 상승시간 구분력 검토

풀업이 1개일 때와 2개(병렬)일 때 라인 상승시간이 2배 차이 나는 것을 이용해
**모듈 전원 인가 여부**를 판별할 수 있는지 계산한다. 버스 용량 50/100/200 pF,
폴링 분해능 12/25 ns 조건에서 구분 가능 여부를 표로 출력한다.

```bash
python sim/tools/i2c_rise_time_sim.py
```

> ⚠ **실기에서는 무효였다.** 계산상으로는 구분 가능하지만, 실제 펌웨어는 폴링에
> `gpio_get_level()`(HAL 함수)을 써서 1회 호출이 상승시간보다 오래 걸린다.
> 측정값이 `SDA=0 SCL=0`(=첫 읽기에 이미 HIGH)으로 나와 분해능이 부족했다.
> 쓰려면 **GPIO 레지스터 직접 읽기**로 폴링 루프를 다시 짜야 한다.
> 기록 보존용으로 남긴다.

## 관련 펌웨어 진단 도구

- **`build.ps1 -OledTest`** — OLED 단독 부팅 테스트(`test/somfy_cases/oled_only_test.c`).
  Matter/Thread/BLE/RF/버튼/배터리를 **전혀 초기화하지 않고** OLED 만 구동한다(~100ms 부팅).
  I2CDIAG(핀 pull 특성) → bit-bang 전체 스캔 → 교차배선 재시도 → force-drive 순으로 진단.
- **`[OLEDMON]`** (60초 주기) — 전송/실패 누적, 페이지 보냄/건너뜀, `present`, free heap.
- **`[BBFAIL]`** — 비트뱅 전송 실패(20회마다 1줄).

## 함정 (실제로 당한 것들)

- **로그 인코딩은 캡처 경로마다 다르다.** pyserial 직접 캡처 = **UTF-8**,
  빌드 로그(`logs/*.log`) = **CP949**. 틀리게 디코드하면 한글 에러가 **0건으로 오독**된다.
  `try utf-8 → except cp949` 로 판별할 것. 이것 때문에 "에러 0, 해결됨"이라고
  잘못 판단한 적이 있다.
- **부팅 ~100ms 구간 로그는 USB-JTAG 이 버린다.** 진단값은 static 에 저장해 두고
  나중에(루프에서) 다시 출력해야 확실히 보인다.
- **긴 한글/기호가 섞인 로그 줄도 유실**된다. 중요한 측정값은 **짧은 ASCII 한 줄**로
  찍을 것(`XCONN sda=%d>%d scl=%d>%d SHORT=%d`).
- "에러가 0건"은 **정상의 증거가 아니다.** OLED 가 미검출이면 flush 자체를 건너뛰어
  에러도 안 난다. `present=1` 과 전송 카운터 증가를 함께 봐야 한다.

# 부록 — `bat_pct_display_sim.py` (배터리 % 표시)

"배터리를 안 꽂았는데 **78%** 로 표시된다" 를 고친 로직을 플래시 전에 검증한다.

```bash
python sim/tools/bat_pct_display_sim.py
```

## 왜 하필 78% 인가

배터리를 빼도 충전 IC(MCP73831)가 BAT+ 를 무부하로 **약 3,970 mV** 로 띄운다.
이 값을 OCV-SoC 곡선에 넣으면 정확히 78% 가 나온다:

```
3850mV=60%, 3980mV=80% 구간 보간
60 + 20 × (3970-3850)/(3980-3850) = 78.4% → 78%
```

**전압만으로는 실제 배터리 78% 와 구분이 불가능하다.** 유일한 단서는
"전압이 오르는가"(무배터리 float = 안 오름 / 충전 중인 셀 = 오름)이고,
이 판정은 5분 창이 차야 나온다 → 그전 5분간 78% 가 보였다.

## 수정 — 애매할 때만 숨긴다

```
ambiguous = (3940 <= mv <= 4010) and USB연결
표시 = "--%"                if (첫 판정 전) and ambiguous
       0%                   elif 미연결 판정
       _bat_mv_to_pct(mv)   else
```

float 창 **밖**이면 충전 IC 가 그 값을 만들 수 없어 배터리 존재가 전압만으로
확정되므로 **대기 없이 즉시** % 를 보여준다. 실제로 배터리를 꽂은 사용자는
거의 기다리지 않고, 배터리가 없는 경우만 5분 뒤 0% 로 확정된다.

| 시나리오 | 0분 | 3분 | 10분 |
|---|---|---|---|
| 무배터리 + USB (문제 상황) | 78% → **--%** | 78% → **--%** | 0% → 0% |
| 실배터리 78% + USB (충전중) | 77% → **--%** | 78% → **--%** | 80% → 80% |
| 실배터리 40% + USB | 40% → **40%** | 41% → 41% | 43% → 43% |
| 배터리 구동(USB 없음) | 78% → **78%** | 78% → 78% | 78% → 78% |

(각 칸은 `수정전 → 수정후`)

## ★창(5분)을 줄이면 안 된다

충전 상승률이 ≈9.3 mV/5분 이라, 창이 짧으면 전반/후반 평균차가 판정 문턱(4 mV)에
못 미쳐 **진짜 충전 중인 배터리를 "미연결"로 오판**해 0% 로 표시한다.

| 창 | 전반/후반 평균차 | 문턱 4mV 대비 |
|---|---|---|
| 1분 | 0.9 mV | 오판 |
| 2분 | 1.9 mV | 오판 |
| 3분 | 2.8 mV | **오판** |
| **5분** | **4.7 mV** | **안전** |

→ "첫 창만 3분으로 단축" 은 안전해 보였지만 실제로는 위험하다. 이 표가 그 근거다.
